Server or phone

Two ways to use the app, never mixed: with an RSS server (tt-rss today, FreshRSS or Miniflux later) as the source of truth, or with the phone fetching feeds itself. Extras (the reading list, curated lists) live on the phone in both. Competitors, clickable proposals, persona critiques, and a build order. Every feed, host and account here is made up, except well-known public feeds from the starter packs.

Written version: server-mode.md. Earlier work: tt-rss in newspapeRSS.

Plan and log

One question per cycle, each ending with something to look at. No app code changes; this page and docs/research/server-mode.md are the output.

What they do

  • One account at a time is the Android norm (Read You, Readrops, Capy). You choose up front or in Settings, and the list shows that account.
  • Nobody merges local and server feeds into one list. NetNewsWire allows both at once, but as separate sections.
  • When the two overlap, the server wins (Fluent Reader), and the app's own settings for the feed are kept.
  • Add goes to the current account. Only NetNewsWire asks which account, because it has several at once.
  • Moving between accounts is OPML nearly everywhere. Only NetNewsWire moves feeds inside the app.
  • A local-only app says nothing about servers (Feeder): no account words anywhere.

What it means here

  • The owner's two setups are what the field already does. The mixed screen built in cycles 77–79 is the odd one out.
  • Pick the setup once, in onboarding, and change it in Settings, like Capy and Readrops. Don't guess it from what's connected.
  • With a server, Add subscribes on the server. Only the category is asked, since there's only one account.
  • A one-tap "move your phone feeds" would be ahead of the field. It's worth it: the people who need it already have both today.
  • Carry paper settings by address (Fluent Reader). When a feed moves, its article text, cap and left-out choice come with it.
  • Without a server, Sources looks like Feeder: no tt-rss row, no server words.

What the server APIs allow (from the tt-rss API reference and earlier research)

  • tt-rss: subscribeToFeed(feed_url, category_id) (category 0 is Uncategorized), unsubscribeFeed(feed_id), getCategories. There's no call to create a category or import OPML. The status codes subscribe returns (already subscribed, added, invalid address, no feed found, several feeds found, couldn't download) are from memory of tt-rss's source, not the reference page.
  • Google Reader API (FreshRSS, Miniflux, Inoreader): subscription/edit adds a feed and sets its label. Adding a label that doesn't exist creates it, so categories can be made from the app.
  • FreshRSS and Miniflux give each feed one category; Inoreader allows several folders (memory). A list grouped by category must put a feed under one heading only.

Adding a site with a server

Add a site asks for an address, as today. The phone finds the feed first, using the same feed finder as today, so tt-rss gets the feed's own address and never "several feeds found". Then Subscribe in your tt-rss, with a category (the last one used), and a snackbar once tt-rss has accepted it. The new row says "Waiting for tt-rss's first fetch".

When it can't go on the server

  • The site has no feed: "Save this page to your reading list". If the address is a curated list the app can read (Arts & Letters Daily), "Add it as a curated list".
  • tt-rss can't fetch it (some sites block servers, or the server is on a home network the site can't reach): "Fetch it from this phone instead", labelled as such under On this phone, or save the page. The one exception to "never mixed"; an open question for the owner.
  • Already subscribed: "Already in your tt-rss, in Science."

With a server, the starter packs and OPML import are hidden: tt-rss imports OPML itself (Preferences › Feeds).

Critique of this comparison · cycle 7 · and what changed

  • The P1 cost was rated "none" while it needs a "Not in your paper" page. Fixed: it reuses the left-out page with a different filter; the table says so.
  • Build step (b) silently depended on (a)'s setting. Fixed: the build order says each step's dependencies.
  • Default 2 had an edge: an existing user whose tt-rss source is paused, or has every feed left out, mostly uses the phone, yet would land in the server setup. Kept the rule (a tt-rss account means the server setup; nothing moves) and listed it as an open question. It's rare, and the Settings switch is one tap.
  • "Leaving brings your feeds" was in the recommendation but in no build step. Fixed: it's step (e), after tonight; tonight's leaving is today's Remove, worded honestly.
  • The comparison scored TalkBack for P1 without a concrete count. Fixed: about 62 stops, but heading navigation gets to any category in at most 8.
  • The phone-fetch exception was presented as decided. Fixed: it's an open question; step (c) ships the reading-list and curated-list fallbacks first.

Decided for the owner (defaults; the critique kept all three)

  • The choice is explicit: asked in onboarding and changeable in Settings, never guessed from what's connected.
  • An existing tt-rss user with phone feeds lands in the server setup, with a one-tap "Move your N phone feeds to tt-rss". Nothing moves without that tap; until then the phone feeds keep working under On this phone. Migration rule: a tt-rss account exists → server setup; otherwise phone.
  • The reading list and curated lists stay on the phone in both setups, under On this phone with a server, and in the plain list without.

(c) Adding a site to the server, with fallbacks

Screens
The Add dialog's server variant: paste an address; the phone finds the feed (today's finder, including "Which part of this site?"); then "Subscribe in your tt-rss" with a Category picker ("To add a category, make it in tt-rss first"); then "Asking tt-rss…" and a snackbar with Undo. Fallbacks: no feed → "Save this page to your reading list" (exists today) or "Add it as a curated list" when it matches one; tt-rss can't fetch it → save the page (and the phone-feed exception if the owner says yes); already subscribed → "Already in your tt-rss, in Science." With a server, the starter packs and OPML import and export are hidden.
Data
TtrssClient.subscribeToFeed(url, categoryId) and unsubscribeFeed(id) in :core, with the status codes mapped to messages; getCategories exists. A DataStore lastCategoryId. After subscribing, run FeedSync.listFeeds so the row appears ("Waiting for tt-rss's first fetch"), which also gives Undo its feed id.
Removed
With a server: adding a phone feed from Add, starter packs, and the OPML menu items.
Risks
tt-rss fetches the feed before it answers, so a slow server can time out; run it as work that outlives the dialog. API level (subscribe needs 5+). The status codes are from memory of tt-rss's source; check them against a real server. Depends on (a) and (b).
